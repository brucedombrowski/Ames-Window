# DM-2026-002: SBOM format is CycloneDX

| | |
|---|---|
| Date | 2026-11-11 |
| Status | Approved by the repository owner, recorded in GitHub issue #7 |
| Affects | REQ-1.1, REQ-1.2; `sbom.cdx.json`; `scripts/sbom.sh` |

## Purpose

A machine-readable component inventory was required. Two open formats satisfy
the NTIA minimum elements and are accepted under Executive Order 14028.

## Options considered

1. **CycloneDX** (OWASP; ECMA-424). JSON, XML or protobuf. Native Rust
   generator maintained by the CycloneDX project. Can carry vulnerability
   and exploitability statements (VDR, VEX) in the same document.
2. **SPDX** (Linux Foundation; ISO/IEC 5962). Strong licence-compliance
   heritage. Rust generators exist but are community maintained.
3. **Cargo.lock alone.** Already committed, already pins every version and
   checksum, but in Cargo's own format with no licence or supplier data.

## Decision

Option 1, CycloneDX 1.6 JSON, generated by `cargo-cyclonedx` at a pinned
version. `Cargo.lock` remains the source of truth that the SBOM is derived
from.

## Rationale

- Both standards are open and freely available. CycloneDX's Rust generator is
  maintained by the standard's own project, which matters for a pinned,
  reproducible toolchain (NIST SP 800-218 PO.3.2).
- Security tooling that an assessor is likely to use (Dependency-Track, Grype,
  Trivy, GitHub dependency submission) ingests CycloneDX directly.
- The ability to attach VEX statements later means "we ship X but are not
  exposed" can be delivered in the same file, which is the question an
  assessor asks after an advisory.
- Option 3 fails NTIA minimum elements on supplier, licence and the
  dependency relationship in a standard form.

## Consequences

- Generator version is pinned in both the script and CI because output bytes
  can change between versions (REQ-1.3).
- A fixed `SOURCE_DATE_EPOCH` is used so the timestamp does not defeat
  reproducibility; freshness is tracked by git, not by the field. See
  DM-2026-003.
- Amended 2026-11-11 (issues #21 and #26): two files are generated in this
  format. `sbom.cdx.json` remains the inventory for every target at once,
  215 components, which is an audit view and describes no single build.
  `sbom-web.cdx.json` is what Cargo resolves for the browser build, 54
  components, and is the SBOM given for a release, which ships that build.
  It lists slightly more than is delivered (build-time tools) and does not
  list what is not a Cargo component: the toolchain, the generated
  JavaScript glue, the page. The Software Version Description names those.
- If a recipient requires SPDX, `cargo sbom` can emit it from the same
  lockfile; the decision is about the committed canonical form, not an
  exclusive one.
