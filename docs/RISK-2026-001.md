## Detail

### RISK-1: Network code evades the automated charter checks

**Statement.** If an engineer introduces network capability through a path the tooling does not see, for example a renamed import of the standard library's socket types, then the charter claim 'no network capability' stated in every SVD becomes false without CI noticing.

**Source.** DM-2026-001 Consequences

**Controls.** deny.toml catches every third-party path. The CI grep catches the obvious standard-library forms. Second-person review is the control for the rest, which is why Standard changes still require a reviewer.

**Review.** When REQ-3.2 is enforced (issue #9) or when the grep is extended

**References.** #8, docs/DM-2026-001.md

### RISK-2: Unmaintained component in the dependency tree

**Statement.** If a component we ship stops receiving fixes, then a vulnerability found in it later has no upstream remedy and must be handled by replacing the component.

**Source.** RUSTSEC-2026-0192, ttf-parser via winit's Wayland title decorations

**Controls.** Weekly advisory scan surfaces the condition. Resolved by DM-2026-006: the winit feature that pulled the font parser was replaced, removing the component.

**Review.** Re-opens automatically if cargo deny reports a new unmaintained advisory

**References.** #6, docs/DM-2026-006.md

### RISK-3: Compromise of the public component registry

**Statement.** If crates.io or a maintainer account is compromised and a malicious version of a component we use is published, then the next deliberate dependency update could pull it in. Versions already pinned are protected by their checksums.

**Source.** Discussion of supply chain threat model, 2026-11-11

**Controls.** Checksums protect pinned versions. A malicious new version only enters on an update, which is a Normal change with review. Advisory scanning catches it after disclosure, not before. Vendoring (cargo vendor) or recorded audits (cargo vet) would prevent it and were considered in DM-2026-005.

**Review.** At each release, or if the project is adopted for a real deployment, when DM-2026-005 is revisited

**References.** docs/DM-2026-005.md, docs/DM-2026-002.md

### RISK-4: Second-person review is practised but not enforced

**Statement.** If a change is merged to main without review, because nothing in the repository configuration prevents it, then an error or an unwanted change reaches the main line with no second pair of eyes and the audit trail shows no approval.

**Source.** REQ-3.2 and REQ-3.4 open

**Controls.** No automated control yet. CODEOWNERS is committed; the branch ruleset is a repository setting only the owner can enable.

**Review.** Closes when issue #9 is done and REQ-3.2 and REQ-3.4 carry evidence

**References.** #9

### RISK-5: Documentation drifts from the software it describes

**Statement.** If counts, versions and status quoted in documents and briefings are typed by hand, then they are wrong soon after they are written and an assessor finds the prose contradicting the artifacts.

**Source.** Deck and README numbers were hand-typed before facts.json existed

**Controls.** sbom.cdx.json, VER-2026-001.md, RISK-2026-001.md and facts.json are generated and drift-checked in CI. The SVD is generated per commit. Prose that quotes a number cites facts.json and the commit it was taken from.

**Review.** When the deck is next regenerated

**References.** docs/facts.json, scripts/facts.sh

### RISK-6: Dependency surface is large relative to the application

**Statement.** If the executable carries far more third-party code than its function needs, mostly platform windowing support, then the attack surface, licence exposure and advisory noise are all larger than necessary, and each component is a place a future vulnerability can appear.

**Source.** SBOM review, 2026-11-11

**Controls.** Inventory and scanning make the surface visible. DM-2026-006 removed the font-parsing subtree. Further reduction means dropping platform features the project does not ship, a Normal change per platform.

**Review.** At each winit or softbuffer update

**References.** docs/DM-2026-006.md, sbom.cdx.json

### RISK-7: Public repository exposes the process in full

**Statement.** If the repository is public, then every requirement, decision, accepted risk and open item is visible to anyone, including which controls are not yet enforced.

**Source.** Charter: the repository is a compliance demonstration

**Controls.** Carrying this risk is the better choice. The visibility is the purpose: the method is meant to be lifted into other projects. Mitigating by going private would remove the value entirely, and a half measure (hiding only the open items) would make the record dishonest. The real exposure is bounded by the CM plan boundary: anything that would be CUI for a real deployment, such as named people, devices, destinations or system boundaries, is kept out of this repository by rule. Cost of mitigation: the project. Cost of carrying: none beyond keeping that boundary.

**Review.** If the repository is ever used as the instance for a real deployment rather than the method

**References.** docs/configuration-management.md

### RISK-8: Single hosting platform for code, issues, releases and CI

**Statement.** If GitHub is unavailable, changes policy, or the account is lost, then the issue trail, release assets and CI history are unreachable until restored, and no change can be merged under the process in the meantime.

**Source.** Architecture review, 2026-11-11

**Controls.** Carrying this risk is the better choice. Git is distributed: every clone holds the full history, the SBOM, the requirements, the register and the generators, so every document except the issue thread is reproducible from any clone with no platform at all. Mitigating with a second platform and a mirror adds a synchronisation process and a second place for records to diverge, which is itself a configuration-management risk. The residual, loss of the issue thread, is reduced by referencing issue conclusions in the decision memoranda, which are in the tree. Cost of mitigation: a mirror, a sync, and a second audit log. Cost of carrying: an outage delays merges and loses nothing permanent that is in the tree.

**Review.** Annually, or if the repository becomes the system of record for a real deployment

**References.** docs/DM-2026-003.md

### RISK-9: Duplicate versions of the same component in the tree

**Statement.** If several versions of one component are compiled in because different dependencies pin different ranges, then the executable carries redundant code, each copy is a separate place for a vulnerability to appear, and advisory scanning may flag a version that a newer sibling has already fixed.

**Source.** cargo deny bans: warning[duplicate] on about a dozen components at 2026-11-11

**Controls.** Scanning covers every copy, so nothing is missed, but the surface is larger than it needs to be. Planned mitigation: a reviewed cargo update as a Normal change, reconciling versions where the dependency graph allows, with a decision memorandum recording what could not be reconciled and why. This risk is carried deliberately into the first release so that the next release can show a risk opened, fixed, closed and every submittal regenerated.

**Review.** At the first release after v0.1.0

**References.** deny.toml [bans] multiple-versions, sbom.cdx.json
