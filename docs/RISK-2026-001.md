### RISK-1: Network code evades the automated charter checks

**Statement.** If an engineer introduces network capability through a path the tooling does not see, for example a renamed import of the standard library's socket types, then the charter claim 'no network capability' stated in every SVD becomes false without CI noticing.

**Source.** DM-2026-001 Consequences

**Controls.** deny.toml bans a list of 21 networking crates and denies the network features of two more; it is a list, not a proof, and a networking crate not on it would pass. Two locked components for the Linux desktop build contain socket code: x11rb, for remote X displays, and rustix, built with its net feature. Whether the application can reach either has not been traced (tracked in issue #47). The CI grep catches the ordinary standard-library and browser forms in our own source. For the browser build, scripts/no-network.sh fails the build if the bundle names a network API and the page's Content-Security-Policy refuses outside connections; for the Windows program, scripts/windows-imports.sh fails if it imports a library outside a short list. Those three are tripwires. The README says what the first two cannot see, and the third's limits are in its own header. Independent review (REQ-3.2) is practised but not enforced by the repository, so it is not counted as a control here.

**Review.** When REQ-3.2 is enforced (issue #9); when the x11rb path is traced; at each release

**Decision.** Repository owner, 2026-11-11, on issue #17: "Human concurs." The residual then stated was Very Low / Moderate. The Technical Lead's response on the same issue was given after the decision. The owner concurred with a residual of Very Low / Moderate. Applying the Technical Lead's later advice, the register now rates it Low / Moderate and states the risk more fully. The changes were put back to the owner on the issue on 2026-11-11; until the owner answers there, the concurrence stands for the risk as it was first stated, not as it is now rated.

**References.** #8, #17, docs/DM-2026-001.md

### RISK-2: Unmaintained component in the dependency tree

### RISK-3: Compromise of the public component registry

**Statement.** If crates.io, a maintainer account, a build tool installed from crates.io (wasm-bindgen-cli, cargo-cyclonedx), the Rust toolchain or a GitHub Action used by the workflows is compromised, then a malicious version could be pulled in: for a component, at the next deliberate update; for a build tool, which is pinned by version but not by checksum, if that version's contents were replaced; for the toolchain and for Actions, which follow a moving channel or tag, at the next run. Versions of components already pinned in Cargo.lock are protected by their checksums.

**Source.** Discussion of supply chain threat model, 2026-11-11

**Controls.** Checksums protect pinned component versions, and only crates.io is an allowed source. None of the controls lowers the chance of adopting a malicious new version: a new version enters on an update, which is a Normal change with review; advisory scanning and the malware scan catch what is already known, after disclosure. Build tools are installed from crates.io at a pinned version on each run with no checksum recorded here, and GitHub Actions are pinned by tag, which can be moved, not by commit. The impact is High because build scripts and procedural macros run on the developer's machine and in the release job, which holds the permissions to sign and publish. Vendoring (cargo vendor) or recorded audits (cargo vet) would prevent it and were considered in DM-2026-005. Independent review (REQ-3.2) is not counted, being unenforced.

**Review.** At each release, or if the project is adopted for a real deployment, when DM-2026-005 is revisited

The owner concurred with a residual of Very Low / High. Applying the Technical Lead's later advice, the register now rates it Low / High and states the risk more fully. The changes were put back to the owner on the issue on 2026-11-11; until the owner answers there, the concurrence stands for the risk as it was first stated, not as it is now rated.

**References.** docs/DM-2026-005.md, docs/DM-2026-002.md, #18

### RISK-4: Second-person review is practised but not enforced

**Statement.** If a change is merged to main without review, because nothing in the repository configuration prevents it, then an error or an unwanted change reaches the main line with no independent review and the audit trail shows no approval.

**Source.** REQ-3.2 and REQ-3.4 open

**Controls.** No automated control yet. Independent review is practised on every pull request, by a person or by an agent holding a reviewer's role (DM-2026-007), and recorded as a comment; nothing in the repository's configuration requires it. A CODEOWNERS file and a branch ruleset are both still to do; the ruleset is a setting only the owner can enable.

**Review.** Closes when issue #9 is done and REQ-3.2 and REQ-3.4 carry evidence

**References.** #9

### RISK-7: Public repository exposes the process in full

**Statement.** If the repository is public, then every requirement, decision, accepted risk and open item is visible to anyone, including which controls are not yet enforced.

**Source.** Charter: the repository is a compliance demonstration

**Controls.** Carrying this risk is the better choice. The visibility is the purpose: the method is meant to be lifted into other projects. Mitigating by going private would remove the value entirely, and a half measure (hiding only the open items) would make the record dishonest. The real exposure is bounded by the CM plan boundary: anything that would be CUI for a real deployment, such as named people, devices, destinations or system boundaries, is kept out of this repository by rule. Cost of mitigation: the project. Cost of carrying: none beyond keeping that boundary. The boundary between what may be public and what may not is procedural: nothing scans for a breach of it, and secret scanning is off for the repository.

**Review.** If the repository is ever used as the instance for a real deployment rather than the method; or on any breach of the boundary

### RISK-8: Single hosting platform for code, issues, releases and CI

**Statement.** If GitHub is unavailable, changes policy, or the account is lost, then the issue trail, release assets and CI history are unreachable until restored, and no change can be merged under the process in the meantime.

**Source.** Architecture review, 2026-11-11

**Controls.** Carrying this risk is the better choice. Git is distributed: every clone holds the full history, the SBOM, the requirements, the register and the generators, so every document in the tree is reproducible from any clone with no platform at all. Mitigating with a second platform and a mirror adds a synchronisation process and a second place for records to diverge, which is itself a configuration-management risk. The residual, loss of what lives only on the platform, is reduced by referencing issue conclusions in the decision memoranda, which are in the tree. Cost of mitigation: a mirror, a sync, and a second audit log. Cost of carrying: an outage delays merges and loses nothing permanent that is in the tree. What lives only on the platform, and in no clone: the issue threads, the pull request reviews that are the record of approval, the Human's concurrences, and the build provenance attestations. The 'every clone is a copy' argument rests today on one owner and no forks.

**Review.** Annually, or if the repository becomes the system of record for a real deployment

**Decision.** Repository owner, 2026-11-11, on issue #20: "Concur" The residual then stated was Low / Low. The Technical Lead's response on the same issue was given after the decision. The rating is the one concurred with. The control note has since been made fuller on the Technical Lead's advice.

**References.** docs/DM-2026-003.md, #20

### RISK-9: Duplicate versions of the same component in the tree

**Statement.** If several versions of one component are compiled in because different dependencies pin different ranges, then the executable carries redundant code, each copy is a separate place for a vulnerability to appear, and advisory scanning may flag a version that a newer sibling has already fixed.

**Source.** cargo deny bans: warning[duplicate] on about a dozen components at 2026-11-11

**Controls.** Scanning covers every copy, so nothing is missed, but the surface is larger than it needs to be. Planned mitigation: a reviewed cargo update as a Normal change, reconciling versions where the dependency graph allows, with a decision memorandum recording what could not be reconciled and why. It was carried deliberately into the first release, v0.0.1, so that a later release can show a risk opened, fixed, closed and every submittal regenerated.

**Review.** At the next release after v0.0.1

**References.** deny.toml [bans] multiple-versions, sbom.cdx.json
