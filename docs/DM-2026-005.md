# DM-2026-005: Dependencies are not vendored; registry compromise is an accepted risk

| | |
|---|---|
| Date | 2026-11-11 |
| Status | The repository owner, as Human, concurred with accepting RISK-3 on 2026-11-11 in issue #18. The Technical Lead's response on that issue is advice, and its corrections are carried in the register |
| Affects | RISK-3; REQ-1.5, REQ-1.6 |

## Purpose

`Cargo.lock` protects every pinned version with a SHA-256 checksum, so a
registry that serves altered bytes for a known version is refused. It does
not protect against a malicious *new* version published under a legitimate
name, which would enter on the next deliberate update. A decision was needed
on whether to prevent that or accept it.

## Options considered

1. **Vendor the dependencies** with `cargo vendor` and commit the source.
   Builds use only the committed tree. A registry compromise cannot reach
   the build; an update is a reviewable diff of third-party source.
   Costs: the repository grows by the full source of every component, every
   update is a large diff, and the vendored tree itself must be kept in sync.
2. **Record audits with `cargo vet`.** Each component version is marked as
   audited by a named person or imported from a trusted audit set. The
   build fails on an unaudited version. Costs: an audit backlog for the
   current tree and ongoing effort per update.
3. **Accept the risk** with the existing controls: checksums for pinned
   versions, crates.io as the only source, advisory scanning, and review of
   every update as a Normal change.

## Decision

Option 3 for now. Recorded as RISK-3 with response "accept", owner the
repository owner, reviewed at each release and whenever the project is
adopted for a real deployment.

## Rationale

- This repository is a compliance demonstration. The application has no
  network capability and handles no data, so the impact of a compromised
  component is bounded to the demonstration itself. NIST SP 800-39 §3.4
  permits acceptance where residual risk is within tolerance and the
  decision is documented and owned.
- The marginal protection of options 1 and 2 applies only at update time,
  and updates are already a reviewed Normal change. The reviewer sees the
  version bump and the advisory scan result.
- Both options remain available and are documented here, so a future
  adoption can reverse this with one memorandum. Option 1 is the simplest to
  explain to a security team and would be the first choice.

## Consequences

- RISK-3 stays open in the register with its review trigger.
- Dependency updates are never automated or auto-merged. The CM plan
  classifies them as Normal.
- If the risk is later mitigated, this memorandum is superseded by a new one
  and RISK-3 is updated, not deleted.
