# DM-2026-003: Generated documents are build outputs, not committed files

| | |
|---|---|
| Date | 2026-11-11 |
| Status | Approved by the repository owner |
| Affects | REQ-4.1, REQ-4.2; `scripts/svd.sh`; `.github/workflows/security.yml` |

## Purpose

The Software Version Description names the commit it describes. A decision
was needed on whether the rendered SVD is committed to the repository or
produced at build and release time. The same question applies to any
document that embeds facts about the current commit.

## Options considered

1. **Commit the rendered SVD.** Readers find it in the tree. But the commit
   that adds it changes the hash it names, so it is stale on arrival, and
   every later commit makes it more so.
2. **Generate at build time; attach to CI runs and releases.** The document
   is never in the tree. It is reproducible from any commit by running the
   script, and the release carries the copy for that version.
3. **Commit at release time only**, in the same commit that bumps the
   version, and have CI verify it matches. Readable in the tree at tags;
   stale between them.

## Decision

Option 2 for the SVD and any document that names the commit. Option 3-style
committed-and-checked files are used only for artifacts whose content does
not depend on the commit hash: the SBOM (derived from `Cargo.lock`) and the
verification matrix (derived from file contents, checked by `scripts/ver.sh
--check`).

## Rationale

- NIST SP 800-53 Rev. 5 SA-5 asks for documentation that is accurate for the
  system as delivered. A document that is wrong the moment it is committed
  fails that by construction.
- NIST SP 800-53 Rev. 5 SA-10 and SP 800-218 PO.3 favour documentation
  produced by the same automation that produces the software.
- The split rule is simple to state: if regenerating a file on the next
  commit would change it even though nothing it describes has changed, it is
  a build output.

## Consequences

- `target/svd/` is ignored by git. CI uploads the SVD beside the SBOM on
  every run; the release workflow (issue #10) will attach it to releases.
- The SBOM and `VER-2026-001.md` stay committed, each with a `--check` mode
  that fails CI on drift.
- A reader who wants the SVD for the current commit runs `scripts/svd.sh`.
  This is documented in the README.
